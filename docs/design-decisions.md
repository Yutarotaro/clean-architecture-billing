# あえて省いたもの

サンプルとして読み切れる分量に収めるため、意図的に実装していないものがあります。
「気づかなかった」のではなく「判断して外した」ものを、理由とともに列挙します。

## ドメインの穴

### 減額時の返金・クレジット残高

プラン変更で差額が負になった場合（ダウングレード）、このサンプルは**何もしません**。
新しい料金は次の請求期間から適用されます。

```python
if proration.net.is_positive:
    invoice = Invoice.issue(...)
# net が 0 以下なら請求書を作らない
```

実務では、顧客ごとに**クレジット残高**を持ち、次回請求から差し引くのが普通です。
それには `CustomerBalance` という 4 つ目の集約と、請求時に残高を消費する手順が要ります。
ドメインの構造は増えますが、レイヤーの説明としては新しいことが出てきません。

### 税・割引・複数通貨の同時運用

`Money` は通貨を持ちますが、実際に扱っているのは JPY だけです。
消費税、クーポン、従量課金は入っていません。
どれも請求書の明細を増やす方向の話で、**日割り以上に面白い設計判断が出てこない**と判断しました。

### ドメインイベントの購読側

集約はイベントを記録し、`pull_events()` で取り出せますが、
**それを購読して何かをする仕組みは実装していません**。

```python
subscription.pull_events()
# [SubscriptionEvent(name="subscription.canceled", ...)]
```

実務ではここからメール送信や分析基盤への転送につながります。
ポートを 1 つ足して `EventPublisher` を注入すればよく、
すでに示したポートの使い方の繰り返しになります。

## インフラの穴

### 本物の決済代行

`PaymentGateway` ポートは切ってありますが、実装は `FakePaymentGateway` だけです。
Stripe の adapter を書くなら `infrastructure/payment/stripe_gateway.py` を足し、
合成ルートの 1 行を差し替えます。

```python
gateway=gateway or FakePaymentGateway(),   # ここだけ変える
```

### webhook の署名検証

`POST /webhooks/payments` は誰でも叩けます。
実運用では `Stripe-Signature` ヘッダの検証が必須です。
これは「この HTTP リクエストが本物か」という**境界の関心**なので、
presentation / adapter 層で完結します。ユースケースには影響しません。

### 認証・認可

ありません。「顧客 A が顧客 B の請求書を見られない」を実装するなら、
ユースケースに呼び出し元の主体を渡すか、クエリ側でフィルタをかけます。
どちらにするかは設計判断ですが、レイヤー構造そのものは変わりません。

### マイグレーション

`create_schema` / `CreateSchema` でテーブルを作っています。
本番では Alembic や golang-migrate に置き換える前提です。
サンプルを 1 コマンドで動かせることを優先しました。

### Go 版の DynamoDB

Python 側で 3 実装を示したので、Go 側は memory と SQLite の 2 つに留めています。
Go で書くこと自体は難しくありませんが、テストに DynamoDB Local（Java）が必要になり、
CI が重くなる割に**新しく分かることがありません**。
[永続化の閉じ込め](persistence-portability.md) で論じた 4 つの漏れは言語に依存しません。

## 運用の穴

### 決済結果の反映漏れを拾い直すバッチ

[決済呼び出しをトランザクションの外に出した](adr/0005-charge-outside-transaction.md)結果、
「請求書は発行できたが決済結果の反映前にプロセスが落ちる」窓が開いています。

残された `open` な請求書を後から拾い直すバッチが本来は必要です。
冪等キーがあるので、決済が実は成功していた場合も二重課金にはなりません。
**設計上その回復が可能であること**までは示しましたが、バッチ自体は書いていません。

### DynamoDB のトランザクション上限への対処

`_expire_past_due` は複数の契約を 1 トランザクションで更新します。
DynamoDB では 100 項目が上限なので、101 件目で落ちます。

正しくは「1 件 1 トランザクション」に寄せるべきでした。
これは**実際に残っている設計の不備**であり、
[抽象の漏れの実例](persistence-portability.md#2-トランザクションのサイズ上限)として
そのまま置いてあります。

### 可観測性

Go 側に `slog` が入っている程度で、メトリクスもトレースもありません。
決済代行の応答時間や、更新バッチの滞留は本番では必ず見たい数字です。

### 並行実行の検証

楽観ロックの衝突は逐次的に再現しています。
実際のレースコンディションの検証には `go test -race` や負荷試験が要ります。

## 「省かなかった」もの

逆に、サンプルだからと省略したくなるが**省かなかった**ものも挙げておきます。
これらを省くと、サンプル全体の主張が成立しなくなるからです。

- **インメモリ実装のトランザクション意味論**。
  「テスト用だから commit はなくていい」とすると、
  commit を書き忘れたユースケースがテストでは通って本番で壊れます。
- **楽観ロック**。3 実装で意味論を揃えたことで、
  [衝突の検出タイミングが実装ごとに違う](persistence-portability.md#4-衝突がいつ分かるか)
  という重要な漏れが見つかりました。
- **冪等キーの必須化**。HTTP ヘッダを任意にすると、いつか誰かが渡し忘れます。
- **時刻の tz-aware 強制**。naive な `datetime` を 1 つ受け入れた時点で、
  どこかで 9 時間ずれます。
