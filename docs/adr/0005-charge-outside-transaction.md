# ADR-0005: 決済 API の呼び出しをトランザクションの外に出す

**状態**: 採用

## 文脈

プラン変更のユースケースは、次のことを順に行います。

1. 契約のプランを変更する
2. 差額の請求書を作る
3. 決済代行に課金を依頼する（**外部 HTTP**）
4. 結果を請求書と契約に反映する

素直に書けば、これらを 1 つのトランザクションで囲みたくなります。
そうすれば「全部成功したか、全部なかったことになるか」が保証されるからです。

## 決定

**トランザクションを 2 つに分け、あいだで決済 API を呼びます。**

```python
with uow_factory() as uow:
    # 請求書を発行して commit
    ...
    uow.commit()

result = gateway.charge(...)          # トランザクションの外

with uow_factory() as uow:
    # 結果を反映して commit
    ...
    uow.commit()
```

`application/charging.py` と `internal/usecase/charging.go` の `charge_invoice` /
`chargeInvoice` がこの形になっています。

## 理由

**DB のトランザクションを開いたまま外部 HTTP を叩くと、
相手が 30 秒応答しないあいだ行ロックを握り続けます。**
平常時は動きますが、負荷が上がった瞬間に接続プールが枯渇し、
決済代行の遅延がそのままサービス全体の停止になります。

これは「トランザクションは短く」という原則の、最も分かりやすい違反例です。

## 結果

**良かったこと**: 決済代行が遅くても、DB の接続は解放されています。
また、この形にしたことで DynamoDB 版がそのまま動きました。
DynamoDB のトランザクションは書き込みしか含められないので、
最初から外部呼び出しを外に出す設計になっていたのが幸いしました。

**引き受けたこと**: **「請求書は発行できたが決済結果の反映前にプロセスが落ちる」窓が開きます。**

この状態では、請求書が `open` のまま残ります。回復手段は用意してあります。

- 冪等キーが請求書に付いているので、決済が実は成功していた場合も**二重課金にはなりません**
- 残された `open` な請求書を後から拾い直せます

ただし**拾い直すバッチ自体は実装していません**
（[あえて省いたもの](../design-decisions.md#決済結果の反映漏れを拾い直すバッチ)）。
設計上その回復が可能であることまでを示した、という整理です。

**別の選択肢**: 完全にやるなら Outbox パターン（決済の指示を DB に書いてから
別プロセスが実行する）や Saga です。
そこまで行くと、このサンプルの主題であるレイヤー分割の話から遠ざかると判断しました。
